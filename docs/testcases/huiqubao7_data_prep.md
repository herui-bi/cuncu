## 二、订单状态与可复用性

| 状态 | 含义 | 所在页签 | 是否可复用 |
| --- | --- | --- | --- |
| `paid` | 已支付，保单 `paidWaitInsure` | 已支付 | 可复用（查看/选择类） |
| `waitPay` | 待支付 | 待支付 | 约 30 分钟自动关闭，禁止跨轮复用、禁止写死订单号 |
| `rebates` | 部分退款（部分保单 `refundedRevoked`） | 部分退款 | 可复用；已退款被保人无操作按钮 |
| `refunded` | 全额退款 | 已退款 | 可复用；仅验证「仅查看详情」 |
| `closed` | 已取消/超时关闭 | 已取消 | 可复用 |
| `closedReverso` | 冲正关闭 | 已取消 | 可复用 |

消耗型用例（043~047、多人升级）会**真实退款**原订单保单，执行后订单变成 `rebates` / `refunded`，
不可再用于需要 `paid` 的用例，必须一例一单；执行顺序由 `conftest.py` 的 `pytest_collection_modifyitems`
统一保证：查看/选择 → 金额/提示 → 多人升级 → 支付。

## 三、造数操作路径

1. **个账支付（医保）造已支付订单**
   - 收银台医保渠道展示为「个账支付」，底层 `payMethod=ybpay`。
   - 测试环境可用个账支付完成真实支付，产生「已支付」医保订单。这是当前唯一能造出医保已支付订单的路径。
   - 升级支付阶段只 mock `ybPay` 接口（`mock_yb_payment`），成功后跳 `#/partSuccess`。
2. **微信支付订单**
   - mock 仅作用于前端（JSAPI 回调 + H5 支付链接），后端订单仍为 `waitPay`，无法造出「已支付」。
   - 微信订单只能由外部真实支付产生，需提前准备。
3. **升级版/尊享版已支付订单**
   - 对基础版已支付订单执行真实升级 + 真实支付（个账/微信）；或直接购买对应产品。
   - 升级产生的待支付订单若不支付，30 分钟后关闭，不构成数据。
4. **部分退款订单**
   - 在订单详情对某一位被保人点「申请退款」，成功后订单变 `rebates`，
     可验证「已退款被保人不可升级 / 升级页仅展示未退款被保人」。
5. **待支付订单**
   - 由升级或投保流程实时生成，支付页停留期间有效；用例按页签动态匹配，页签为空则 skip。

## 五、查数 SQL（只读）

```sql
-- 订单（表名按订单号末位 0-9 路由）
SELECT order_no, status, pay_method, amount, number, product_code, create_time
FROM mth_insure_core.insure_order_<末位>
WHERE order_no = ?;

-- 保单
SELECT policy_id, product_code, status, premium
FROM mth_insure_core.insure_order_policy_<末位>
WHERE order_no = ?;

-- 账号下可用订单（0~9 分表分别执行）
SELECT order_no, product_code, status, pay_method, amount, number, create_time
FROM mth_insure_core.insure_order_<0..9>
WHERE user_id = ? AND project_code = 'CITY000110-1' AND status IN ('paid','rebates');
```

库连接：`utils/db.py` + `config/environments/huiqubao/<env>.yaml`；仅执行 SELECT。

## 六、常见问题

- **登录页被「是否以投保人信息快速注册或登录」弹窗遮挡**：`open_home` 会自动点「手动注册登录」；页面改版时需同步选择器。
- **升级订单生成失败且升级历史表无记录**：多为原订单已被整单退款；改为从详情单个被保人进入升级，由前端自动退款所选保单。
- **医保退款失败（提示医保账户异常）**：优先重试或换新订单，升级退款依赖原医保账户状态。
- **报告出现数据类失败**：先确认订单状态是否漂移（超时关闭/被其他消耗型用例退款），再判定是否脚本问题。
